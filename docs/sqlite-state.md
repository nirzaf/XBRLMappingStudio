# Local SQLite state and connector

## Application database

The application creates `${LocalApplicationData}/XBRLMappingStudio/state.db` on first use. The version is stored in `PRAGMA user_version`; migration 1 creates the base settings, project registry, run journal, publication receipt, and suggestion audit tables. Migration 2 adds durable review-decision metadata. Migration 3 adds the validated artifact digest to the run journal and publication receipt so validation evidence remains tied to the final digest. Foreign keys are enabled on every connection. WAL mode is enabled for the local single-workspace deployment, with a five-second SQLite busy timeout and connection pooling disabled. Schema changes run in an explicit transaction. A database with a newer schema is refused without changing its contents.

`.xmap` remains the portable source of truth for executable graphs. SQLite stores local operational state and metadata, not graph definitions or secrets. The run journal imports legacy JSON journal records once without deleting the old files. Finalized run entries and publication receipts, including the validated digest, are committed together. `LocalApplicationDatabase.IntegrityCheck()` exposes SQLite's integrity check. Unix app-data directories are set to owner-only access and database files to owner read/write; Windows inherits the user's application-data ACL.

`BackupTo(path)` uses SQLite's online backup API for a consistent snapshot and refuses to overwrite a prior backup, including under concurrent calls. Its temporary database is created with owner-only Unix permissions before any state is copied. Keep backups outside the live application directory. To restore, exit the application, move the current `state.db` and any `state.db-wal` and `state.db-shm` files out of the live path, then copy the verified backup into place. Migrations 1 through 3 are additive; future destructive migrations must first create and verify a backup.

## SQLite data source and target

The adapter opens source databases read-only. It discovers user tables, inspects columns, samples rows, and streams rows with cell lineage. Before execution, SQLite rows are sorted by canonical field content, and run manifests fingerprint that same ordered input. This makes execution and full-source digests independent of SQLite's unspecified scan order while avoiding a raw database-file hash that can be blocked by Windows file sharing or omit active WAL contents. Preview fingerprints cover only preview rows and are marked non-replayable; full runs fingerprint all rows. Provenance row locators are query-position numbers and are not stable row identities; tables without a configured key do not receive a stable row identity. Table names are quoted as identifiers. Numeric values declared as binary floating point are rejected; exact financial decimals should be stored as invariant text and listed in the binding's `decimalColumns` configuration.

`SqliteTargetPublisher` writes a batch in one immediate transaction using prepared values and a configured business key. It requires that key to match a non-partial primary or unique index with BINARY collation; expression and other-collation indexes are rejected because they cannot match the emitted conflict target. It rejects missing/null and duplicate batch keys, and accepts exact decimal fields only when the destination column has TEXT affinity. The target database contains `xms_idempotency_receipts`; a replay with the same operation key and effective input intent returns the stored receipt, while changed intent returns `PUB006`. Row writes and the receipt commit together. Cancellation, constraint failures, and process exceptions roll back the transaction. The shared application service wires SQLite destination preview and publication into both CLI and Desktop workflows; provider-wide and mixed-destination reconciliation remain incomplete.

## Scope

This is a local SQLite implementation, not qualification of SQL Server, PostgreSQL, MySQL/MariaDB, or Oracle. Taxonomy FTS5 indexing, automated retention/cleanup, cross-process writer stress qualification, and Windows ACL verification remain open. The application database stores run state, publication receipts, and durable suggestion-review audit; the project registry table is reserved for future workspace indexing.
